    How-To: VM and Chaos Testing

    This guide provides operational recipes for running multi-distribution integration tests, managing QEMU/KVM virtual machines, and executing Watchdog chaos monkey routines.

    1. Multi-Distribution Docker Integration Testing

    Execute automated integration test suites across containerized Linux environments:

    # Run the Debian 13 integration test suite
make integration-debian

# Run the Fedora 44 integration test suite
make integration-fedora

# Run the Arch Linux integration test suite
make integration-arch

# Run all integration test suites sequentially
make integration-all

    These targets launch disposable VMs, with a fresh directory under target/integration-vm/ for each run. The DNS/UDP containment gate uses controlled receivers and external captures, with calibrated IPv4 and IPv6 paths. It does not infer containment from public resolver/STUN timeouts or require an exit to resolve a diagnostic server's AAAA record. Inconclusive measurements fail; an integration failure is not automatically rerun into a green result.

    The same three userspaces run in CI on every push and pull request, inside a disposable Fedora 44 kernel VM. This isolates privileged containers from the runner's kernel and AppArmor policy store. It does not measure native AppArmor or a Debian/Arch kernel. No kernel LSM is disabled to run the matrix. To reproduce:

    VM_WORK=/tmp/ttp-integration-new scripts/vm/run_integration_vm.sh debian

    The work directory must not exist. The VM needs KVM, QEMU, genisoimage, Python, OpenSSH and Internet access, uses 4 GiB RAM and a sparse 20 GiB disposable disk, and records the kernel/engine versions and integration log. Native AppArmor is qualified separately below. A container has no real boot, so these tests cannot show native lifecycle behaviour; section 3 covers that. Running the direct container commands on an AppArmor host refuses managed Tor: container policy namespace delegation is not implemented.

    For local runs, VM_IMAGE_CACHE=/path/to/official-image.qcow2 can reuse a cached base image. The fixture still fetches the distribution's checksum list and verifies the copied image before booting. A mismatched cache is refused. scripts/vm/run_integration_tests.sh is the internal VM-side runner; the controller explicitly marks that environment disposable before it may configure the private DNS/UDP test links.

    2. QEMU/KVM Virtual Machine Orchestration

    For full kernel-level, DNS mount, and systemd integration testing, use the provided QEMU/KVM VM management scripts:

    Spawning a Test VM

    # Launch an Arch Linux VM instance
./scripts/vm/start.sh arch

# Launch a Debian VM instance
./scripts/vm/start.sh debian

    Syncing Codebase and Taking Snapshots

    # Sync local TTP source code into the running VM
./scripts/vm/send.sh

# Save a named VM snapshot before executing intrusive tests
./scripts/vm/snapshot.sh arch save before-fsm-test

# Restore the VM snapshot after testing completes
./scripts/vm/snapshot.sh arch restore before-fsm-test

    3. Lifecycle Transitions in a Disposable VM

    scripts/vm/lifecycle/run.sh takes a TTP session through shutdown, reboot and suspend/resume onto a new network, and judges each from a packet capture QEMU writes outside the guest. It needs KVM, qemu-system-x86_64, genisoimage and curl, and no root:

    VM_WORK=~/.cache/ttp-lifecycle-vm scripts/vm/lifecycle/run.sh
# the same on a guest whose network is managed by NetworkManager
VM_DISTRO=fedora VM_WORK=~/.cache/ttp-lifecycle-vm-fedora scripts/vm/lifecycle/run.sh

    VM_DISTRO is debian (default; Debian 13, systemd-networkd) or fedora (Fedora 44, NetworkManager, SELinux enforcing). It downloads that cloud image once (verified against the distribution's published checksum list; the list's signature is not checked), installs TTP from the working tree, and writes results.txt, one capture per phase and state snapshots into $VM_WORK. scripts/vm/lifecycle/egress.py <file.pcap> summarises a capture by destination; it streams the file, so size is not a concern. Transient download errors receive up to three retries. Downloads remain bounded by connection/transfer timeouts; checksum mismatches still fail the run. Guest readiness requires successful cloud-init completion. A timeout or error stops provisioning and records cloud-init.txt, including guest diagnostics; SSH availability alone cannot declare the VM ready. The guest preserves its image hostname. A completed cloud-init run with code 2 is accepted only if its structured report has no fatal errors and its only recoverable warnings concern setting the hostname. Other warnings, malformed evidence, installation failures and timeouts are refused; Docker must also start and answer successfully. The automated Debian downloads use the dated official build 20261103-2651 and matching dated QCOW2 filename, avoiding changes to the latest aliases. Lifecycle captures are header-only; continuous chaos observations use full frames. Both cover scenario phases, never provisioning.

    scripts/vm/lifecycle/chaos.sh runs the watchdog chaos sweep (tests/chaos_monkey.py, options through CHAOS_ARGS, e.g. CHAOS_ARGS="--reset-between --no-bypass") in the same kind of guest, detached, because two of its faults cut the SSH session on purpose. It collects the log and exit code through QEMU Guest Agent over virtio-serial, independently of SSH and the guest's firewall. Failure to retrieve the result remains an error; it never counts as containment.

    Both scripts run in CI from .github/workflows/lifecycle.yml. See docs/security-assessment.md section 4.3 for what it asserts and what it found.

    Required VPN with real Tor

    scripts/vm/vpn/run.py provisions two fresh Debian 13 cloud VMs. One runs a WireGuard peer, DHCP and Internet forwarding; the other runs NetworkManager, the required VPN and TTP. Nothing changes the host's firewall or resolver. The client's provisioning NIC is disabled before measurements. QEMU Guest Agent controls the protected guest over virtio-serial, so the test needs no SSH exception in the VPN guard.

    Requirements: Python 3.12+, KVM access, qemu-system-x86_64, qemu-img, genisoimage, OpenSSH and Internet access from the guests. Supply the official Debian 13 genericcloud AMD64 image and its matching published SHA512SUMS:

    mkdir -p target/vpn-qualification
python3 scripts/vm/vpn/run.py \
  --base /path/to/debian-13-genericcloud-amd64.qcow2 \
  --checksums /path/to/SHA512SUMS \
  --work target/vpn-qualification/debian-unique-run

    The work directory must not exist. The base image is read-only and its checksum is checked before boot; this harness does not authenticate the checksum list's signature. Obtain both from the Debian cloud image service. Source installation uses the repository's hashed dependency locks. Only tracked files are copied into the guest. Public network or Tor failures fail the run; there is no automatic fallback to an offline success.

    The peer also exposes a controlled HTTP server directly on the physical path. The external QEMU capture must detect that direct path before protection and after explicit stop. During protection it accepts only ARP, DHCP and UDP to the exact VPN endpoint. Unknown traffic, fragments, truncated evidence and empty captures fail visibly. A real non-exempt HTTPS request must resolve its hostname and return IsTor=true; encrypted tunnel packets must be observed. The harness also checks DHCP renewal, tunnel loss, verified emergency containment, reconnection without reopening and explicit stop with guard removal. Each phase ends with a controlled ARP request so that even an isolated guest must produce observable link-layer traffic. This adds no IP exception. DHCP renewal requires a matching DHCPREQUEST/DHCPACK transaction, not just retries. The JSON report marks protected phases explicitly. A protected start phase counts violations from the moment the guard exists: the harness polls for inet ttp_vpn and then sends an ARP marker, and frames before it (for example the kernel's own MLD reports) are reported as before_marker. The marker trails the guard by one nft poll, a few milliseconds; a missing marker is inconclusive. Explicit stop ends the guarantee and checks guard/intent removal and zero Tor main/control PIDs; its capture may contain physical traffic from restored resolver services.

    The peer also counts packets it receives, independently of any reply: cleartext requests arriving through the tunnel at an inner canary (10.9.0.1:8000, and [fd09::1]:8000 for a dual-stack tunnel), new TCP connections (SYN) it forwards to the Internet, and connections to an optional private bridge. Before protection, a request through the tunnel must increment the inner counter; while protected, application requests into the tunnel must leave it at zero. Tor's own relay traffic must increment the forwarding counter, which proves that counter can observe.

    Select the underlay and tunnel families with --topology:

    Topology Underlay WireGuard endpoint Tunnel and TTP flag
    v4-v4 (default) IPv4, DHCPv4 IPv4 IPv4, --no-ipv6
    v4-dual IPv4, DHCPv4 IPv4 IPv4 and IPv6
    v6-v4 IPv6, RA and stateful DHCPv6 IPv6 IPv4, --no-ipv6
    v6-dual IPv6, RA and stateful DHCPv6 IPv6 IPv4 and IPv6
    dual-v4 Both IPv4 IPv4, --no-ipv6
    dual-dual Both IPv6 IPv4 and IPv6

    For an IPv6 underlay the observer additionally accepts exactly the VPN guard's IPv6 control exceptions: DHCPv6 546 → 547 and router/neighbor solicitation or advertisement with hop limit 255. Every other IPv6 frame, including MLD, extension headers, fragments and ICMPv6 errors, is a violation while protected. Renewal requires a DHCPv6 Renew or Rebind answered by a Reply with the same transaction ID. Direct canaries are checked in every underlay family. The guests have no public IPv6 route: IPv6 is qualified on the underlay and inside the tunnel, and Tor still reaches its relays over IPv4.

    After the Tor/DNS checks the harness runs ttp check six times while an unrelated nftables table is created and deleted every three seconds, which makes the watchdog re-evaluate repeatedly. Any emergency or watchdog verdict, or a latched emergency afterwards, fails the run; an inconclusive public-Tor probe (exit 3) does not. This reproduces a check that once sampled the watchdog mid-evaluation and contained a healthy session.

    Right after the tunnel drops, before the watchdog latches emergency (whose table has no NAT chain), the redirect still holds and Tor cannot forward. The harness opens redirected connections there and leaves them as orphaned sockets (timed-out HTTP clients and clients closing with unread data). It targets the families TTP redirects: IPv4, and IPv6 only with a dual-stack tunnel, since --no-ipv6 drops IPv6 instead. Before explicit stop at least one orphan must still exist. After ttp stop it observes for 60 seconds: any packet to a canary or to a loopback destination on the physical link fails the run, because it belongs to a connection redirected during the session. Without the teardown's socket closure, v6-dual reproduced this leak in every run.

    --bridge starts a private, unpublished obfs4 bridge on the peer and starts TTP with --use-bridges and that bridge line. Tor must verify IsTor=true while the peer counts bridge connections through the tunnel and no forwarded TCP connection: every relay connection went to the bridge. All forwarded TCP segments are reported too; a stray segment of a connection opened before the session is not a relay connection. This qualifies the managed Tor's obfs4 transport child under the VPN guard. It does not qualify snowflake, meek or the public bridge distribution.

    --transitions adds suspend/resume and reboot. A continuous probe repeatedly requests the direct and tunnel canaries as root, as nobody and, on the direct route only, as Tor's UID; its unprotected control must produce visible direct packets and inner-tunnel arrivals. With protection active, the guest then suspends to RAM for longer than the DHCP lease and WireGuard's session limit, and the capture covers the whole sleep and resume. A second protected session is rebooted: QEMU pauses the guest at its reboot request, so the capture covers the entire shutdown sequence with the probe running. After boot the harness requires no retained session, guard, intent or table, then starts a new session.

    The same scenarios run on relevant pull requests, weekly and on demand in .github/workflows/vpn-vm.yml, as one job per topology plus bridge and transition jobs. CI uploads reports and captures, excluding disks and seed images.

    Evidence is in results.json, guest version reports, phase logs and external client/*.pcap files. Debian runs do not qualify ParrotOS, Fedora, GUI sessions, Wi-Fi roaming or real provider networks. See the VPN validation table for each gate.

    Native Parrot and AppArmor qualification

    The same two-VM harness also accepts a separately prepared Parrot client and a native development DEB. The Debian peer remains unchanged. Optional raw UEFI code is read-only; its matching variable template is copied per guest. Disks preserve the base image's virtual size, including Parrot's 64 GiB Btrfs image.

    python3 scripts/vm/vpn/run.py \
  --base /path/debian-13-genericcloud-amd64.qcow2 \
  --checksums /path/debian/SHA512SUMS \
  --client-base /path/parrot-prepared/disk.qcow2 \
  --client-checksums /path/parrot-prepared/SHA512SUMS \
  --client-os parrot --client-memory 3072 \
  --client-firmware-code /path/OVMF_CODE.fd \
  --client-firmware-vars /path/OVMF_VARS.fd \
  --client-deb packaging/transparent-tor-proxy_0.5.1_all.deb \
  --require-apparmor --work /path/new-parrot-run

    The DEB filename carries the version in pyproject.toml. This command does not publish a package or tag. Build the current working tree with packaging/build_deb.sh first.

    Prepare the client in a disposable overlay of the official Home image, keeping the original read-only. Verify the original signed hashes and the signing key's full fingerprint using Parrot's verification instructions. For Home 7.4, the pinned primary fingerprint is B711822346552E4D92DA02DF7A8286AF0E81EE4A. Verify the signature and fingerprint before accepting the compressed image's SHA512, then decompress it. Preserve the overlay's backing image and directory relationship; a checksum of the overlay alone does not authenticate its backing chain.

    The prepared guest needs cloud-init, openssh-server, sudo and qemu-guest-agent, with SSH available for provisioning. Configure a headless multi-user.target if required by the image; preserve NetworkManager, AppArmor and distribution security settings. Install the current verified Parrot archive key if the image's packaged key has expired. Shut down the guest before hashing the prepared overlay with sha512sum disk.qcow2 > SHA512SUMS. The harness checks this derived checksum separately; retain the original signature evidence, image digest and preparation log alongside it.

    With --require-apparmor, an AppArmor-free guest cannot pass. In addition to the VPN scenarios, the harness requires actual ttp-tor (enforce) evidence, starts another protected session, changes the loaded policy to complain mode inside the disposable guest, and requires the watchdog's verified emergency to identify AppArmor as its cause. Returning to enforce mode must leave the emergency latched. The external capture checks this fault phase too.

    The November 2026 local qualification passed on headless Parrot Home 7.4 using the native DEB, NetworkManager 1.52.1, Tor 0.4.9.15, Python 3.13 and kernel 7.1.13+parrot7. It covered public Tor/DNS, DHCP renewal, tunnel loss/reconnection, explicit stop and the AppArmor mutation. This does not qualify GUI interaction, Secure Boot, other editions, bridge transports or other IPv6 topologies. See AppArmor's contract and limits.

    Both QEMU processes are stopped on normal completion or an exception. The private work directory (mode 0700) retains disks and captures for investigation; the guest disks contain throwaway WireGuard keys. Share the reports and captures, not VM disks or cloud-init material. Captures retain the first 768 bytes of each frame, sufficient to inspect the DHCP exchange; treat them as test data.

    4. Executing Watchdog Chaos Monkey Testing

    The Watchdog Chaos Monkey suite simulates live system faults, abrupt process terminations, table deletions, and /etc/resolv.conf target modifications while TTP is active:

    # Execute full Watchdog fault injection suite
make chaos-monkey

    The VM wrapper observes all eight injections continuously on TCP, UDP and DNS in both families, including the interval before recovery audits. It retains full external captures and calibrated controls. Privileged removal of enforcement can expose traffic before repair; that exposure remains a leak in the report even when recovery succeeds. See continuous fault evidence for the exact contract, sampled cadence and artifacts. The standalone make chaos-monkey recovery audits alone do not measure this initial interval.
